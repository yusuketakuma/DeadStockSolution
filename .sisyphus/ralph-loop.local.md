夜間の無人リファクタリングを実行してください。

目的:
repo 全体をスキャンし、重大な問題から順に、実装変更と検証まで完了させること。
分析だけで終わらず、Done 条件を満たすまで止まらないこと。

優先順位:
1. セキュリティリスク
2. システム安定性・信頼性
3. ビルド時間・開発フィードバック時間の短縮
4. 可読性・保守性の改善
5. 複雑な処理と意味的に重複したコードの集約

必須タスク:
- コードベース全体を横断スキャンして改善候補を自動抽出する
- 優先順位付きバックログを作る
- 最重要項目から順に、調査 → 計測 → 修正 → 検証 → 再スキャンを繰り返す
- 必要なら専門エージェントや局所 refactor ワークフローを使う
- 1回で満足せず、high priority が片付くまで続行する

重点:
- セキュリティ: 認証/認可不備、秘密情報漏洩、注入、危険なデシリアライズ、パストラバーサル、SSRF、権限昇格、機密ログ
- 安定性: クラッシュ要因、null/edge case、競合状態、リソースリーク、壊れた再試行、タイムアウト不備、トランザクション不整合、フレーク
- ビルド時間: build / test / lint / typecheck / bundle の重い経路を先に特定し、変更前ベースラインを取ってから改善する
- 重複コード: 意味的に同じ責務の重複だけを集約する。表面的に似ているだけの処理は無理に共通化しない
- 可読性: 長大関数、過剰分岐、密結合、死んだコード、隠れた副作用、不明瞭な命名を改善する

ガードレール:
- 振る舞いを変えない安全な改善を優先する
- 大規模 rewrite、見た目だけの整理、フォーマット churn、命名遊び、投機的抽象化は禁止
- build 時間短縮のために、テスト削除、型チェック無効化、lint 無効化、品質低下を伴う近道は禁止
- 共通化によって分岐や責務混在が増えるなら却下する
- リスクの高い変更では、先に characterization test や安全網を追加する
- 公開 API、データ契約、永続化仕様、認証認可フローは、重大修正に必要で検証可能な場合を除いて壊さない
- 本当にブロックされた場合以外は止まらない

検証:
- 変更ごとに可能な限り test / lint / typecheck / build / diagnostics / static analysis を実行する
- build 時間改善は、同じコマンドで変更前後を比較し、差分を記録する
- 失敗した検証は放置せず、修正するか、外部要因なら exact な原因を記録する
- 重要モジュールは修正後に再スキャンする

- ビルド時間について、主要コマンドの変更前後比較があり、再現可能な改善が入っているか、改善不能理由が明確
- 意味的に妥当な重複コード集約が行われ、無理な抽象化はない
- 変更箇所は以前より単純で読みやすく、テストまたは検証が強化されている
- test / lint / typecheck / build を可能な最大範囲で通す。通らないものは exact な原因と残件を残す
