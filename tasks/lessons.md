### 3) 共通ラッパー化の副作用
- 症状：`AppAlert` を関数ラッパー化した際に `AppAlert.Heading` が消え、型エラーが発生
- 原因：Bootstrapコンポーネントの静的サブコンポーネント互換を確認せず置換した
- 防止策：共通ラッパー導入時は `rg -n "<Wrapper\\.([A-Z])"` で静的メンバー利用箇所を事前監査し、typecheck前に置換方針を確定する

### 4) テストモックの過剰マッチ
- 症状：`url.includes(path)` により意図しないAPIが成功扱いになり、回帰検知が弱化
- 原因：パス一致条件が曖昧（部分一致）
- 防止策：テストモックは `pathname` の厳密一致（必要時のみquery一致）を原則とし、未マッチは `404` を返す

### 5) レスポンシブ切替のDOM重複
- 症状：Desktop/Mobile両UIを同時描画し、テストの要素重複や重い描画が発生
- 原因：CSS非表示だけで切替しており、Reactツリーは両方評価していた
- 防止策：共通切替コンポーネントで `matchMedia` を使い、表示側のみ描画する

### 6) ブレークポイント不整合と未移行残し
- 症状：`AppResponsiveSwitch` の判定幅と全体CSSの切替幅が一致せず、768-991pxでUI挙動が分裂した
- 原因：テーブル移行時に「`<AppTable` 残件ゼロ確認」と「ブレークポイント統一確認」を完了条件へ入れていなかった
- 防止策：実装完了前に `for f in $(rg -l "<AppTable" client/src); do rg -q "AppResponsiveSwitch" "$f" || echo "$f"; done` で残件ゼロを確認し、`max-width` 定義は `991.98px` へ統一してから検証を回す

### 7) フロント必須マッピングとバックエンド仕様の乖離
- 症状：`used_medication` アップロードで、存在しない項目（数量/期限）を必須扱いして登録導線が破綻した
- 原因：UI必須フィールド定義と `parseMapping` の許可・必須条件を同時確認していなかった
- 防止策：アップロード必須項目変更時は `client/src/pages/UploadPage.tsx` と `server/src/routes/upload-validation.ts` をペアでレビューし、E2Eで文言と送信条件を固定する

### 8) デフォルト並び順が重い経路を固定
- 症状：一覧画面が常に `sort=priority` を送信し、重い優先度計算経路が常用された
- 原因：画面初期値に「重いが有用なソート」を置いたまま、通常運用の負荷を見積もっていなかった
- 防止策：一覧の初期表示は軽量ソート（例: recent）を標準とし、重いソートは明示選択に分離する

### 9) 管理系再計算APIの同期実行
- 症状：信頼スコア再計算APIが同期実行で、タイムアウト/重複実行のリスクが高かった
- 原因：長時間ジョブを通常APIレスポンスに同居させていた
- 防止策：長時間処理は起動APIを `202 Accepted` 化し、実行中ガードと重複起動抑止を必須ルールにする

### 10) 認証必須設定の未設定がランタイム500化
- 症状：`/api/auth/login` が 500 を返し、`/api/auth/me` が 401 となってログイン不能になった
- 原因：`JWT_SECRET` 未設定時の例外がルート内で汎用 500 扱いになり、設定不備と業務エラーが判別できなかった
- 防止策：認証ルート冒頭で設定チェックを先行実行し、設定不備は `503` + 固定メッセージで返す。加えて JSON パース失敗など 4xx はグローバルハンドラで 500 に昇格させない

### 11) テスト環境依存の認証導線が本番運用と乖離
- 症状：デモ口座の自動シードや `TEST_*` 環境変数依存により、本番運用手順との整合が崩れた
- 原因：アプリ起動時の自動シードと「テスト」命名が残り、運用責務（手動シード・本番設定）が曖昧になっていた
- 防止策：本番運用は手動シード（`npm run db:seed --workspace=server`）を原則にし、環境変数命名を `DEMO_*` に統一する。UI上のワンクリック導線仕様（メールのみ/メール+パスワード）は運用方針に合わせて都度明記し、README/SECURITY/テストの3点を同時更新する

### 12) セキュリティ例外の合意を実装へ反映する手順不足
- 症状：デモ用途の仕様変更（パスワード貼り付け）時に、レビュー指摘と運用合意が衝突しやすい
- 原因：通常ルール（秘密情報のクライアント公開禁止）と、デモ運用の例外条件を同時に文書化していなかった
- 防止策：例外を採る場合はユーザー合意を前提に `SECURITY.md` と `README.md` に適用範囲（デモのみ）を明記し、テスト期待値も同時に更新する
