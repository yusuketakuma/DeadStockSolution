# API 互換性ポリシー

## バージョニング方針

- すべての公開エンドポイントは `/api/v1/` プレフィックスを使用する
- マイナーバージョン内（例: v1.1 → v1.2）では後方互換性を維持する
- 破壊的変更が必要な場合は新しいメジャーバージョン（`/api/v2/`）を追加する

## 破壊的変更の定義

### 破壊的変更ではない（後方互換）
- レスポンスへの新規フィールド追加
- 既存フィールドへのオプション値の追加
- 新規エンドポイントの追加
- レスポンス時間の改善

### 破壊的変更（非互換）
- フィールドの削除または名前変更
- フィールドの型変更（例: `string` → `number`）
- 必須パラメータの追加
- エンドポイントの削除または URI 変更
- HTTPステータスコードの変更
- エラーレスポンス形式の変更

## 破壊的変更の手順

1. **Deprecation 通知**: 変更予定のエンドポイント/フィールドに対して、
   レスポンスヘッダー `X-API-Deprecation` で通知を開始する
2. **移行期間**: 最低 1 マイナーバージョン（例: v1.3 で deprecated → v1.4 以降で削除可能）
3. **CHANGELOG 記載**: 廃止予定と削除のタイミングを `CHANGELOG.md` に明記する
4. **削除実施**: 移行期間終了後にエンドポイントまたはフィールドを削除する

## クライアント通知

### レスポンスヘッダー

```
X-API-Deprecation: /api/v1/old-endpoint は v1.4 で削除予定。/api/v1/new-endpoint に移行してください。
```

### CHANGELOG 記載例

```
## v1.3.0
### Deprecated
- `GET /api/v1/items` — v1.4.0 で削除予定。`GET /api/v1/inventory` を使用すること。
```

## テスト契約

- OpenAPI スキーマは `server/openapi.yaml` で管理する
- CI では `npm run openapi:check` を実行し、スキーマとの乖離を自動検証する
- PR ごとに破壊的変更の有無をチェックし、意図しない変更をブロックする

```bash
# ローカルでの確認
npm run openapi:check
```
